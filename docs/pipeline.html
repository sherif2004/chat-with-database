How the Askbase pipeline works

What happens to one question, step by step, and what each possible outcome looks like. Everything here is taken from the code in app/chat and app/api.

Overview

Every chat request first passes four access gates (A to D), then goes through one LangGraph graph of nine steps. Most steps can end the run early with a message. Solid arrows go to the next step, dashed arrows leave the main path, and the blue loop is the SQL retry.

Want every call in order? Open the full sequence diagrams (browser, gates, pipeline, models, Redis, Qdrant and both databases, with every branch). Steps A to D are the access gates every chat request passes before the graph. RBAC marks where the role matters. Admins also have a tenth path: from the router, a data-change request leaves the read pipeline (section 2).

Access control (RBAC)

Roles are enforced in the application code, in layers. Postgres only stores the role as data (a role column limited to user, supervisor and admin). The backend is the authority. The interface only hides what a role cannot use.

The layers, in the order a request meets them

  1. Origin check (app/main.py). Blocks cross-site writes.
  2. Session (current_user in app/dependencies.py). The cookie is turned into a user. The role is read from the database on every request, so a promotion or demotion applies at once.
  3. Route permission (require_permission("...") in app/dependencies.py). The route names a permission, and has_permission(role, permission) decides. A miss returns 403.
  4. Checks inside the chat pipeline. The chat routes pass can_write (true only with data:write) into the graph. It changes what the router prompt offers, and the router node re-checks it in code so a stray model answer cannot open the write path.
  5. Confirm step (POST /chat/confirm-change). Requires data:write again, and the one-time token must belong to the same admin.
  6. Interface (frontend/src/permissions.js, can()). Hides the Users and Activity pages, the connect form and the admin controls. Not a security boundary.

Related rules

  • Sign-up always creates a user. The role is never read from the request body.
  • The first admin comes from ADMIN_EMAIL and ADMIN_PASSWORD at startup. If that email already has an account, it is promoted, its password is replaced and its sessions end.
  • Role map: app/accounts/permissions.py is the single source of truth. Nothing else should compare role names.
  • What the database enforces: chat queries run in a read-only transaction, so even a write that slipped past the guard would be rejected. The app still connects with one database login for reads and writes, so a leaked DATABASE_URL would bypass every role.

0. Before the graph runs

This is the HTTP layer for POST /chat and POST /chat/stream.

  1. Cross-site check. A write request whose Origin is not in CORS_ORIGINS gets 403. Requests with no Origin (curl) pass.
  2. Session. The session cookie identifies you. No valid session gives 401. Your key is u:<id>, and can_write is true only for admins.
  3. Conversation. With no conversation_id a conversation is created now, with a placeholder title cut from the question, even if the question is later refused. With an id, it must be yours, otherwise 404. If replace_last is set (regenerate or edit), the newest exchange is deleted first.
  4. Title. If the chat still has a placeholder title, a thread asks the cheap model for a better one, in parallel with everything else.
  5. Run. The graph starts with the question, your key, the conversation, skip_cache = replace_last and can_write.

2Answer cache

Redis. No model call.

  • The key is chat_cache:u:<id>:<normalized question>. Normalizing lowercases, drops punctuation and collapses spaces.
  • Skipped when replace_last is set.
  • Hit: the stored response is returned with cache_hit: true and nothing else runs. It is still saved to history.
  • Miss, Redis down, or an unparseable entry: treated as a miss, and the pipeline continues.

3Connection and history

Two branches run in parallel and join before the router.

  • Resolve connection. In order: in-memory cache, the "no saved connection" list (default database), the saved encrypted URL (decrypt, connect, read the schema), then the default database. If APP_SECRET_KEY is missing the saved URL is ignored. If the saved database is unreachable, the result is a connection_error message and the pipeline stops.
  • Load history. The last 3 exchanges of this conversation, with each answer and the SQL used. This is what makes follow-ups like "just for Iron Maiden" work.

4Router

Cheap model. Input: the question, the schema and the history. For admins the prompt also offers data_change.

Model saysResult
greeting, off_topic, unsafeA short reply in the question's language, then stop
data_change, you are not an adminRe-checked in code and turned into unsafe: "I can only answer read-only questions"
data_change, adminGoes to the admin path
data_questionContinues to step 5
Unusable outputFails closed to off_topic

5Few-shot lookup

Embedding model and Qdrant.

Embeds the question and fetches stored question and SQL pairs with similarity of at least FEW_SHOT_MIN_SCORE (0.6). If Qdrant or the embedding call is down, or the store is not ready, the run continues with no examples.

6Generate SQL

Capable model. The prompt holds the schema, the examples, the history and, on a retry, the previous SQL with its database error.

7SQL guard

sqlglot parser. No model call.

  • The SQL must parse, with 1 to 5 statements.
  • Each must be a pure query: a SELECT, a UNION, or a WITH that ends in a SELECT. Any INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, COPY, SET, GRANT or transaction control is forbidden.
  • Tables must be known tables in public. CTE names are allowed.
  • Functions starting pg_, lo_ or dblink, plus set_config, current_setting, version, nextval, setval, currval and a few XML ones, are forbidden.
SituationResult
Unknown tableoff_topic "can't answer" message, then stop
Anything else rejected, or unparseableunsafe message with the reason, then stop
PassesContinues with the normalized statements

A guard rejection is not retried.

8Execution with retry

Read-only. No model call unless it retries.

  • Each statement runs in a read-only transaction with statement_timeout (10 s), fetching at most MAX_ROWS + 1 rows (100 plus one). The extra row only sets truncated.
  • If a pooled connection had dropped, it retries once.
  • The database rejects it (bad column, timeout, anything): the error is saved, the counter goes up, and the flow goes back to step 6 with the failed SQL and the error. The new SQL passes the guard again. Retrieval is not redone.
  • After 3 failed attempts: an off_topic "I couldn't answer that" message, then stop.
  • If any statement fails, the whole attempt is retried.

9Write the answer

Capable model.

It sees the SQL and the first 20 rows of each query, plus the total row count. It must answer in the question's language and only from the results. The response carries every query's full rows (up to 100), the SQL, and one answer sentence. The intent is data_question.

2. Admin data changes

Reached only from step 4, when you are an admin and the router says data_change. The whole path, including the confirm call, with its three RBAC checks:

  1. Generate write SQL (capable model). It can ask for clarification or say it cannot, as in step 6.
  2. Write guard. Exactly one statement, and it must be an INSERT, UPDATE or DELETE. A second write hidden in a WITH is rejected. UPDATE and DELETE need a WHERE. Tables must be known tables in public, so the app schema is blocked. The same forbidden functions apply. An unknown table gives off_topic, and any other rejection gives unsafe.
  3. Dry run. The statement runs in a transaction with the timeout, the row count is read, and the transaction is always rolled back.
Dry-run outcomeResult
Database erroroff_topic: "I couldn't prepare that change: …"
0 rowsoff_topic: "wouldn't affect any rows"
More than MAX_WRITE_ROWS (100)unsafe: narrow it down
1 to 100 rowsA change preview: the exact SQL, the row count and a one-time token (kept in Redis for 300 s)

A preview is never cached, and history stores it without the token.

Confirm: POST /chat/confirm-change (admin only)

  1. The token is taken atomically. Missing, expired or already used gives 410. A token issued to another admin gives 403, and the token is consumed anyway.
  2. If the connected database changed since the preview: 409. If it is unreachable: 400.
  3. The SQL is re-validated by the write guard and committed in one transaction. If the row count differs from the preview, or exceeds the limit, it rolls back with 409. A database error gives 400 and nothing is saved.
  4. On success the answer is "Done. N rows changed." In the background it writes app.data_changes and the activity log, clears cached answers (everyone's if you are on the shared demo database, otherwise only yours), and saves a "Confirmed: …" history entry.

3. After the graph, for every response

  • If a title was requested, the controller waits up to 4 s for it. It is applied only if you have not renamed the chat.
  • The response gets its per-step timings.
  • Background tasks run after the response is sent:
    • save the exchange to history, which also bumps the conversation's time;
    • cache the response in Redis, unless it was a cache hit or a change preview;
    • after a successful step 8 where every query returned rows, store the question and SQL as a few-shot example (skipped if the same question or the same SQL is already stored).
  • On the next screen, if the last answer was a successful data question, the UI calls GET /conversations/{id}/followups for suggested next questions. It returns none otherwise.

4. Streaming

POST /chat/stream runs the same code in a worker thread. As each step starts it sends a stage event: input_guard, cache_lookup, resolve_connection, load_history, router, retrieve_examples, generate_sql, sql_guard, execute_sql or generate_answer. The UI groups these into four stages: reading, writing the query, running it, writing the answer. The stream ends with one done event (the same payload as /chat) or one error event.

6. When something is down

DownEffect
RedisEvery question is a cache miss. The login rate limiter and pending change tokens fall back to memory. Nothing breaks.
Qdrant or embeddingsNo few-shot examples and nothing is learned. Answers still work.
Azure OpenAIAnything that needs a model returns 503. Cache hits and input-guard refusals still work.
Your connected databaseA connection_error message in chat.
The app database (history, logs)Saves fail quietly with a warning, and the response is still sent.

7. Things to know

Refusals are cached too. Everything except change previews is cached for an hour, including refusals, clarification questions and connection_error messages. After your database comes back, the same question can still show the old error until the cache expires, or until you use regenerate, which skips the cache.

Reads and writes use the same database login. Read-only safety comes from the SQL guard plus the read-only transaction, not from a separate database user.
